
# CampusHub 校园互助平台 - 详细设计文档

- **项目名称：** CampusHub 校园互助平台
- **设计阶段：** Phase 3 详细设计文档（整合版）
- **技术架构：** Vue3 + SpringBoot3 模块化单体架构
- **分层架构：** Controller → Service → Repository → Entity
- **最后更新：** 2026-05-17

## 一、设计概述

本项目为 CampusHub 校园互助平台系统设计文档。本次详细设计全覆盖系统 P0/P1/P2 全部业务功能，按照后端标准四层架构拆分，从数据实体、设计模式、业务服务、接口控制四个维度完成全系统类结构梳理，完全满足校园跑腿、技能互助、二手交易、订单流转、实名认证、信用体系、即时聊天、后台管理全流程开发规范。

系统设计视角分为四大核心部分：

- **核心实体与数据库关系（图1）**：涵盖系统底层数据模型及各实体间的物理与逻辑映射。
- **系统设计模式实现（图2）**：通过引入设计模式解决复杂业务状态流转与扩展性痛点。
- **业务 Service 服务层结构（图3）**：定义核心业务逻辑、操作契约及跨模块交互规范。
- **前端请求 Controller 控制层（图4）**：确立符合 RESTful 风格的接口路径、入参与出参规范。

## 三、系统核心设计模式类图实现

### 3.1 策略模式：订单状态流转管控

> **业务痛点：** 订单存在 6 种流转状态（待接单、已接单、进行中、待确认、已完成、已取消），不同状态下用户可执行的操作严格受限。若使用原生 `if-else` 或 `switch` 链硬编码进行判断，代码结构将极其臃肿，且未来新增状态（如“争议中”）时扩展性极差。
>
> **解决方案：** 定义统一订单状态策略接口，每种状态独立实现对应业务权限，通过上下文动态切换策略。

- **顶层策略接口 IOrderStateStrategy**：提供核心校验方法如 `canAccept`、`canComplete`、`canCancel`、`canConfirm` 并在接口内声明获取合法状态流转列表。
- **上下文管理类 OrderStateContext**：自动根据订单当前状态绑定对应策略类，统一对外提供状态权限判断。
- **六大状态策略实现类**：包括待接单策略、已接单策略、进行中策略、待确认策略、已完成策略、已取消策略，各自精细定义专属的操作行为与流转权限。

### 3.2 工厂模式：多类型需求创建校验

> **业务痛点：** 校园跑腿（ERRAND）、技能互助（SKILL）、学习占座（STUDY）、二手物品（SECONDHAND）四类不同版块的需求在创建时校验规则各不相同。例如，跑腿必须有位置标签，二手物品必须有配图。硬编码在业务方法中会造成严重的逻辑耦合。
>
> **解决方案：** 搭建需求工厂类，绑定不同板块专属校验器，发布需求自动匹配规则完成参数校验。

- **校验顶层接口 DemandValidator**：定义统一的校验契约方法 `validate(DemandParam param)`。
- **四大业务板块独立校验实现类**：ErrandValidator（强制位置）、SkillValidator（强制技能标签）、StudyValidator（强制时间段）、SecondhandValidator（强制包含实物配图）。
- **需求工厂 DemandFactory**：统一接收发布参数，根据 `category` 从动态注册的 Map 容器中匹配对应的校验规则，合法后生成正式的需求实体。

### 3.3 观察者模式：业务事件解耦通知

> **业务痛点：** 当订单发生变更（接单、完成、取消）时，系统需要同时执行多项附加操作，如推送站内消息、增减用户信用分值、更新需求整体状态等。若串行编码在服务层中，将引发严重的业务耦合与事务延长问题。
>
> **解决方案：** 基于 Spring 事件发布订阅机制实现业务事件完全解耦。业务核心层仅负责发布相应事件，多个独立的监听类自主处理后续衍生逻辑。

- **订单事件统一发布器**：负责包装订单变更状态并推送事件。
- **消息通知监听器**：异步接收并处理事件，自动封装并向目标用户推送特定的站内通知。
- **信用分值监听器**：根据订单完结或违约事件，调用信用服务进行自动加减分操作。

### 3.4 组合策略模式：智能用户匹配推荐

为发布的校园互助需求智能推荐合适的接单用户，支持地理位置、技能标签、信用分值等多维度综合排序。

- **统一匹配顶层接口 DemandMatcher**：定义用户匹配推荐算法标准。
- **单维度精准匹配器**：位置匹配器（LocationMatcher）、技能匹配器（SkillMatcher）、信用分匹配器（CreditScoreMatcher）。
- **组合综合匹配器**：对上述单维度匹配结果进行加权复合排序，输出最优的智能推荐接单用户列表。

## 四、SOLID 原则审查与修改清单

团队对照面向对象设计的 SOLID 原则，逐条审查了最初由 AI 第一版生成的原始类图，记录了其中违反开发规范与架构设计原则的 7 处严重设计缺陷，并制定并实施了最终的修正方案。

### 4.1 SOLID 审查明细

| 原则 | AI是否违反 | 违反说明 | 修正方案 |
|------|------------|----------|----------|
| **S - 单一职责原则 (SRP)** | 是 (2处) | 1. `OrderService`：同时负责接单、确认、取消、计算信用分变动、发送通知（5项职责）。信用分、通知分别属于用户信用与消息子域，不应高度耦合。<br>2. `DemandService`：既负责需求 CRUD，又内嵌处理标签（Tag）的全面增删改查。 | 1. 拆分职责：将信用逻辑提取至 `CreditService`，通知发送提取至 `NotificationService`。`OrderService` 仅保留订单流转状态和业务编排。<br>2. 拆分标签管理：独立抽出 `TagService`，需求服务仅在创建时通过工厂关联标签。 |
| **O - 开闭原则 (OCP)** | 是 (2处) | 1. 需求创建：`DemandService.createDemand()` 内部通过 `switch(category)` 硬编码判断需求类型并做差异校验，新增板块需改动主干分支。<br>2. 订单流转：状态流转操作在 `OrderService` 中通过庞大的 `if-else` 链条判断 `OrderStatus`。 | 1. 引入工厂模式：定义 `DemandValidator` 接口，并为跑腿、技能、学习、二手实现独立的校验类，由 `DemandFactory` 动态 Map 映射调度。<br>2. 引入策略模式：定义 `IOrderStateStrategy` 接口，为6种状态实现专属策略类。 |
| **L - 里氏替换原则 (LSP)** | 是 (1处) | AI 设计了 `UrgentDemand extends Demand`，重写 `getExpiryTime()` 返回加急截止时间。导致 `DemandService.listDemands()` 统一按过期时间排序时行为不一致，破坏了父类方法契约。 | **用组合替代继承：**<br>1. 彻底移除 `UrgentDemand` 子类。<br>2. 在 `Demand` 实体中新增 `isUrgent` (Boolean) 和 `urgentDeadline` 字段。<br>3. Service 层通过自定义 `Comparator` 统一处理排序。 |
| **I - 接口隔离原则 (ISP)** | 是 (1处) | AI 原始设计定义了一个臃肿的 `ICampusService` 大接口，整合了用户、需求、订单、评价等所有方法。导致 `UserServiceImpl` 被迫实现无关的需求与评价方法，只能空实现。 | **拆分细粒度接口：**<br>解耦拆分为独立的 `UserService`、`DemandService`、`OrderService`、`ReviewService`、`ArbitrationService`、`NotificationService` 等细粒度专业接口。 |
| **D - 依赖倒转原则 (DIP)** | 是 (1处) | 1. `OrderService` 通过 `new NotificationServiceImpl()` 直接创建硬编码依赖，未使用控制反转容器。<br>2. 跨模块场景下，`OrderService` 直接注入了 `DemandRepository`，违反跨模块访问开发规范。 | 1. 改用 Spring 容器的依赖注入机制，通过 `@Autowired` 注入接口。<br>2. 跨模块调用强制改为注入并调用 `DemandService` 的公开方法，严禁绕过业务层直接注入其他模块的 Repository。 |

## 五、架构组件结构设计

### 5.1 Service 业务服务层结构

- **认证权限模块 (auth)**：
    - `AuthService`：处理用户注册、登录验证、登出注销、Token 安全校验。
    - `JwtTokenProvider`：负责 JWT 核心令牌的生成、解析、过期时效核验。
- **用户中心模块 (user)**：
    - `UserService`：提供个人资料信息查询、基本资料修改、公开敏感信息脱敏查询。
    - `CertificationService`：实名认证申请提交、管理员后台审核、用户认证状态追踪。
    - `CreditService`：管理用户信用积分扣减、接单权限门槛校验、信用记录流水追踪。
- **核心业务模块 (experiment)**：
    - `DemandService`：实现互助需求发布、内容编辑、主动取消、分页高级检索与关键词模糊搜索。
    - `OrderService`：控制用户接单流转、标记送达、确认验收、申请取消及 24 小时定时自动确认机制。
    - `ReviewService`：支持完结订单双向评价提交、用户历史评级列表调取。
    - `ArbitrationService`：负责系统低分触发或申诉仲裁工单创建、后台工单处理及待办审计管理。
- **消息通知模块 (notification)**：
    - `NotificationService`：负责全平台异步业务消息创建推送、未读计数统计、单条/全部已读状态打标。
- **即时通讯模块 (chat)**：
    - `ConversationService`：一对一聊天会话生命周期创建、聊天消息实时发送、历史通讯记录轮询调取、会话已读同步。
- **智能推荐模块 (recommend)**：
    - `RecommendationService`：利用组合策略输出用户偏好需求列表、接单用户智能就近匹配。
- **后台管理模块 (admin)**：
    - `AdminService`：提供平台核心数据统计看板、违规用户封禁与解封控制、后台全局列表审计。

#### 3. 发布需求

- **接口路径与方法：** `POST /api/demands`
- **认证要求：** 需提供合法用户 Token，且必须完成实名认证
- **请求体参数说明：**

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| title | String | 是 | 需求标题，2-50字 |
| description | String | ... | 详细描述，10-500字 |
| category | String | 是 | 板块：ERRAND / SKILL / STUDY / SECONDHAND |
| rewardAmount | BigDecimal | 是 | 报酬金额，必须 >= 0 |
| rewardType | String | 是 | 结算形式：MONEY / POINT |
| isUrgent | Boolean | 否 | 是否加急，默认为 false |
| urgentDeadline | String | 否 | 加急截止时间（isUrgent 为 true 时必填） |
| locationTag | String | 是 | 位置（如"南区快递点"、"一教"、"图书馆"） |
| tagIds | Long[] | 否 | 关联标签 ID 列表 |
| imageUrls | String[] | 否 | 需求图片附带的 URL 列表 |

- **板块额外工厂校验规则：**
    - `ERRAND`（校园跑腿）：必须显式填写 `locationTag`。
    - `SKILL`（技能求助）：必须至少关联 1 个技能标签 `tagIds`。
    - `STUDY`（学习互助）：必须填写具体互助时间段信息。
    - `SECONDHAND`（二手物品）：必须在 `imageUrls` 中上传至少 1 张实物外观图片。

#### 4. 浏览需求列表（含高级筛选）

- **接口路径与方法：** `GET /api/demands`
- **认证要求：** 需认证
- **查询 URL 参数：** 包含 `category`、`status`、`keyword`（模糊搜索）、`locationTag`、`isUrgent`、`sortBy`（支持按发布时间、报酬金额或加急截止时间排序）、`sortDir`（asc/desc）以及基础分页参数。

#### 5. 接单操作

- **接口路径与方法：** `POST /api/orders`
- **认证要求：** 需完成实名认证且个人实时信用积分必须 >= 60 分。
- **请求体参数：**

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| demandId | Long | 是 | 打算承接的目标校园需求主键 ID |

- **失败拦截响应：** 若需求已被承接，返回 `40901`；若信用分不足，拦截并返回状态码 `40301`（提示“信用分不足，无法接单”）。

#### 6. 取消订单（带有信用扣分机制）

- **接口路径与方法：** `PUT /api/orders/{id}/cancel`
- **业务机制：** 成功承接订单后 10 分钟内取消，系统判定为无责取消，信用积分不受惩罚；若超出 10 分钟宽限期实施超时违约取消，将触发观察者事件，自动扣除接单服务方 10 分个人信用分。

#### 7. 提交双向评价与差评举证

- **接口路径与方法：** `POST /api/reviews`
- **参数要求：**

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| orderId | Long | 是 | 关联业务订单 ID |
| rating | Integer | 是 | 评分星级，范围 1 - 5 星 |
| content | String | 条件 | 当评分 <= 3 星时，必须填写不少于 15 字的差评原因 |
| imageUrls | String[] | 条件 | 当评分 <= 3 星时，必须至少上传 1 张截图作为证据链 |

- **业务流转：** 评分 <= 3 星的低分差评提交后，系统将通过业务编排自动触发并向后台创建对应的 `ArbitrationTicket` 纠纷仲裁工单，交由管理员进行介入处理。

## 七、数据库设计

### 7.1 物理实体与主外键设计说明

| 数据表 | 主键 (PK) | 关键外键 (FK) / 约束 | 业务设计与范式说明 |
|--------|-----------|----------------------|---------------------|
| `users` | `id` | `username` (UNIQUE)<br>`student_id` (UNIQUE) | 用户账户主表，记录真实姓名、加密凭证及最新信用积分。 |
| `certifications` | `id` | `user_id` → `users.id` (UNIQUE) | 维护一对一实名认证状态，防止单用户存在多条待审核申请。 |
| `credit_records` | `id` | `user_id` → `users.id` | 信用分增减变动历史流水表，追溯变动关联订单。 |
| `demands` | `id` | `publisher_id` → `users.id` | 存储校园需求核心内容、涉及版块、报酬类型及发布状态。 |
| `demand_images` | `id` | `demand_id` → `demands.id` | 维护需求附带配图，采用 `sort_order` 实现内部精确排序。 |
| `tags` | `id` | `name` (UNIQUE) | 全局公共标签字典库（位置、技能标签）。 |
| `demand_tags` | `(demand_id, tag_id)` | 联合主键，分别引用两张表 | 实现需求与标签之间的典型多对多（N:M）关系物理表。 |
| `orders` | `id` | `demand_id` → `demands.id` (UNIQUE) | 一个有效需求最多只能衍生出一笔接单订单，约束互斥。 |
| `order_status_logs` | `id` | `order_id` → `orders.id` | 全量记录订单每一次状态变更流转明细，以便全链路溯源。 |
| `reviews` | `id` | `order_id`, `reviewer_id` (联合唯一) | 双向星级评价表，一笔订单中的一方参与者至多限评一次。 |
| `arbitration_tickets` | `id` | `order_id` → `orders.id` | 针对违约或差评投诉自动/手动生成的管理员仲裁申诉工单。 |
| `notifications` | `id` | `user_id` → `users.id` | 站内个人通知主表。 |
| `conversations` | `id` | 联合唯一索引约束双方 ID | 双方沟通的聊天会话实体，可选择性绑定特定需求主键。 |
| `messages` | `id` | `conversation_id` → `conversations.id` | 会话内的具体聊天消息明细存储表。 |
| `admin_operation_logs` | `id` | `admin_id` → `users.id` | 管理员实施封禁、审批、处理仲裁的审计日志。 |

```sql
);

CREATE TABLE conversations (
    id BIGSERIAL PRIMARY KEY,
    user1_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    user2_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    related_demand_id BIGINT REFERENCES demands(id) ON DELETE SET NULL,
    last_message_content VARCHAR(1000),
    last_message_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT chk_conversation_distinct_users CHECK (user1_id <> user2_id)
);

CREATE UNIQUE INDEX uq_conversation_pair_demand
    ON conversations (
        LEAST(user1_id, user2_id),
        GREATEST(user1_id, user2_id),
        COALESCE(related_demand_id, 0)
    );

CREATE TABLE messages (
    id BIGSERIAL PRIMARY KEY,
    conversation_id BIGINT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    sender_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    content TEXT NOT NULL,
    message_type message_type NOT NULL DEFAULT 'TEXT',
    is_read BOOLEAN NOT NULL DEFAULT false,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE admin_operation_logs (
    id BIGSERIAL PRIMARY KEY,
    admin_id BIGINT NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    operation VARCHAR(200) NOT NULL,
    target_type VARCHAR(100) NOT NULL,
    target_id BIGINT,
    detail TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### 7.3 高频查询索引设计说明

为确保系统在大规模并发及高频数据吞吐下的流畅度，对数据库底层表结构定制了高性能索引方案：

- **`idx_users_phone_hash` 与 `idx_users_status`**：使用手机号带盐不可逆哈希值构建 B-Tree 索引，支持应用层不暴露明文的精确高效去重与状态过滤。
- **`idx_demands_status_created` / `category_status` / `location_status`**：针对用户浏览大厅高频条件组合（按状态、版块、地点、发布时间）设计复合索引，完美规避全表扫描。
- **`idx_demands_keyword` (GIN 倒排索引)**：对需求标题与详情文本进行模糊合并分词，提供高效的站内关键词全文模糊检索支持。
- **`idx_orders_publisher_status` 与 `idx_orders_acceptor_status`**：为个人中心“我的发布”和“我的接单”列表提供极速状态拉取及倒排排序。
- **`idx_messages_conversation_created`**：针对私聊会话中根据聊天时间线倒序上拉历史消息记录设计，保证即时通讯的性能响应。

### 7.4 隐私安全与第三范式合规性

1. **数据隐私加固：** 用户敏感密码绝不存储明文，在应用层统一通过 `BCrypt` 自适应高强度加盐算法哈希后落库；手机号采用字段级对称加密，`phone_cipher` 存密文供页面解密脱敏展示，`phone_hash` 存储防重不可逆哈希。
2. **规范化建模：** 物理设计严格契合关系数据库第三范式（3NF）核心准则，用户、需求、订单、双向评价、系统通知等均完全原子化独立成表。多对多关联通过专门的关系交叉解耦表（如 `demand_tags`）拆解为两个 1:N 关系；状态变更有独立日志追踪，杜绝出现历史变动冗余字段带来的更新异常风险。
