# SOLID 检查清单（Phase 3 任务 1）
## 背景

按照作业要求，先让 AI 根据 P1 需求规格说明书和 P2 架构设计文档生成了一份完整类图，然后团队对照 SOLID 原则逐条审查，记录 AI 原始设计中的违规并给出修正方案。

以下"AI 原始设计"指 AI 第一版生成的类图，"修正后"指团队审查并修改后的最终版本（即提交的类图）。

---

## S — 单一职责原则（Single Responsibility Principle）

**检查问题：有没有类承担了过多职责？**

| 项目 | 内容 |
|---|---|
| AI 是否违反 | 是（2 处） |
| 违反说明 | **第 1 处**：AI 原始设计中 `OrderService` 一个类同时负责接单、确认完成、取消订单、计算信用分变动、发送站内通知，共 5 项不同职责。信用分属于"用户信用"子域，通知属于"消息"子域，不应与订单状态流转混在一起。 |
| | **第 2 处**：AI 原始设计中 `DemandService` 既负责需求的 CRUD，又负责标签（Tag）的增删改查。标签管理是独立的子域，且 Tag 是被 Demand 和 User 等多个实体共用的，不应塞在 DemandService 里。 |
| 修正方案 | ① 将信用分相关逻辑抽到 `CreditService`（addCredit / deductCredit / canAcceptOrder），将通知发送抽到 `NotificationService`，`OrderService` 只保留订单状态流转和业务编排。② 将标签管理抽到 `TagService`，`DemandService` 只在创建需求时通过 `DemandFactory` 关联标签。 |

## O — 开闭原则（Open/Closed Principle）

**检查问题：新增需求类型（板块）或新增订单状态时，是否需要修改现有代码？**

| 项目 | 内容 |
|---|---|
| AI 是否违反 | 是（2 处） |
| 违反说明 | **第 1 处（需求创建）**：AI 原始设计中 `DemandService.createDemand()` 内部用 `switch(category)` 判断需求类型，针对 ERRAND 校验收件地址、针对 SKILL 校验技能类型、针对 STUDY 校验时间段、针对 SECONDHAND 校验图片。如果以后新增第 5 种板块（比如"表白墙"），必须修改这个 switch 块。 |
| | **第 2 处（订单状态流转）**：AI 原始设计中 `OrderService` 的接单、确认、取消等方法内部用 `if-else` 链判断 `OrderStatus`，新增状态（如"争议中"）需要在多个方法中都加分支。 |
| 修正方案 | ① 引入**工厂模式**：定义 `DemandValidator` 接口，ERRAND / SKILL / STUDY / SECONDHAND 各有一个校验实现类，`DemandFactory` 根据 category 从 Map 取出对应 Validator。新增板块只需加一个 Validator 实现类并注册到 Map，`DemandService` 和已有 Validator 不改。② 引入**策略模式**：定义 `IOrderStateStrategy` 接口，6 种状态各一个实现类，`OrderStateContext` 持有当前策略。新增状态只需加一个策略实现类并注册映射，`OrderService` 不改。 |

## L — 里氏替换原则（Liskov Substitution Principle）

**检查问题：子类是否可以无差别替换父类使用？**

| 项目 | 内容 |
|---|---|
| AI 是否违反 | 是（1 处） |
| 违反说明 | AI 原始设计中创建了 `UrgentDemand extends Demand`，重写了 `getExpiryTime()` 方法返回加急截止时间而非普通截止时间。但在 `DemandService.listDemands()` 做排序时依赖 `getExpiryTime()`，导致加急需求的排序行为跟普通需求不一致——加急需求排到列表最后面了。父类的方法契约（返回的是"过期时间"用于排序）被子类破坏了。 |
| 修正方案 | 用**组合替代继承**：去掉 `UrgentDemand` 子类，在 `Demand` 实体上加 `isUrgent`（Boolean）和 `urgentDeadline`（LocalDateTime）两个字段。创建时由 `DemandFactory` 根据 `isUrgent` 决定是否设置加急截止时间。排序逻辑在 Service 层通过自定义 Comparator 统一处理，不再依赖继承。 |

---

## I — 接口隔离原则（Interface Segregation Principle）

**检查问题：有没有接口太"胖"，包含了某些实现类根本不需要的方法？**

| 项目 | 内容 |
|---|---|
| AI 是否违反 | 是（1 处） |
| 违反说明 | AI 原始设计中定义了一个 `ICampusService` 大接口，把用户管理、需求管理、订单管理、评价管理的方法全塞在里面。`UserServiceImpl` 被迫实现 `createDemand()`、`submitReview()` 等跟用户无关的方法，只能空实现或直接抛 `UnsupportedOperationException`。 |
| 修正方案 | 拆分为独立的细粒度接口：`UserService`、`DemandService`、`OrderService`、`ReviewService`、`ArbitrationService`、`NotificationService` 等，每个接口只包含自己领域的业务方法。每个实现类只实现自己需要的接口，不会被迫实现无关方法。 |

---

## D — 依赖倒转原则（Dependency Inversion Principle）

**检查问题：高层模块（Service）是否直接依赖了低层模块的具体实现？**

| 项目 | 内容 |
|---|---|
| AI 是否违反 | 是（1 处） |
| 违反说明 | AI 原始设计中 `OrderService` 通过 `new NotificationServiceImpl()` 直接创建通知服务实例，而不是通过 Spring 依赖注入。另外在跨模块场景下，`OrderService` 直接注入了 `DemandRepository`（其他模块的数据访问层），绕过了 `DemandService`，违反了架构设计文档中"跨模块必须走 Service 接口，禁止直接调用 Repository"的开发红线。 |
| 修正方案 | `OrderService` 对 `NotificationService` 的依赖改为 Spring 接口注入（`@Autowired private INotificationService notificationService`），运行时由容器注入实现。跨模块数据访问改为调用 `DemandService` 的公开方法，不再直接注入 `DemandRepository`。 |

### 修正手段汇总

| 违反原则 | 修正手段 |
|---|---|
| S — 单一职责 | 拆分 Service：抽出 CreditService、NotificationService、TagService |
| O — 开闭原则（需求创建） | 工厂模式：DemandFactory + DemandValidator 接口 + 4 个校验实现类 |
| O — 开闭原则（订单状态） | 策略模式：IOrderStateStrategy 接口 + 6 个状态实现类 + OrderStateContext |
| L — 里氏替换 | 组合替代继承：Demand 实体内嵌 isUrgent / urgentDeadline 字段，去掉 UrgentDemand 子类 |
| I — 接口隔离 | 接口拆分：各 Service 独立定义接口，不再共用大接口 |
| D — 依赖倒转 | 依赖注入：改用 Spring @Autowired 注入接口；跨模块通过 Service 公开方法调用，禁止直接注入 Repository |
