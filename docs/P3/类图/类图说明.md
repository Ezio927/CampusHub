## 1. 设计概述

CampusHub 核心类图覆盖系统 P0/P1/P2 业务功能，围绕校园跑腿、技能互助、二手交易、订单流转、实名认证、信用体系、即时聊天和后台管理进行统一建模。整体设计按后端标准四层架构拆分，使类图既能对应代码实现，也便于说明模块边界。

## 4. 实体关系与基数

| 主体类 | 基数 | 关联类 | 业务含义 |
| --- | --- | --- | --- |
| `User` | 1 : 0..1 | `Certification` | 一个用户可未认证，也可有一条当前实名认证记录。 |
| `User` | 1 : N | `CreditRecord` | 用户信用分的所有增减以流水保存。 |
| `User` | 1 : N | `Demand` | 用户可发布多条校园互助需求。 |
| `User` | 1 : N | `Order` | 用户可分别作为发布方或接单方持有多笔订单。 |
| `Demand` | 1 : 0..1 | `Order` | 一条需求最多生成一笔正式订单。 |
| `Demand` | 1 : N | `DemandImage` | 一条需求可包含多张配图。 |
| `Demand` | N : M | `Tag` | 需求可绑定多个标签，物理层通过 demand_tags 拆分。 |
| `Order` | 1 : N | `OrderStatusLog` | 订单每次状态变化写入一条日志。 |
| `Order` | 1 : 0..2 | `Review` | 订单双方各最多提交一条评价。 |
| `Review` | 1 : 0..1 | `ArbitrationTicket` | 低分评价或申诉可触发一次仲裁工单。 |
| `User` | 1 : N | `Notification` | 每条站内通知归属于一个接收用户。 |
| `User` | 1 : N | `Conversation` | 用户可参与多个与需求相关的会话。 |
| `Conversation` | 1 : N | `Message` | 一条会话包含多条聊天消息。 |
| `User(ADMIN)` | 1 : N | `AdminOperationLog` | 管理员每次后台操作被记录为审计日志。 |

## 5. 系统核心设计模式说明

| 设计模式 | 使用场景 | 业务痛点 | 类图实现 | 设计收益 |
| --- | --- | --- | --- | --- |
| 策略模式 | 订单状态流转管控 | 订单包含 6 种状态，不同状态可执行操作不同，直接用 if-else 会造成分支臃肿。 | IOrderStateStrategy 定义统一状态权限；OrderStateContext 根据当前状态切换策略；各状态策略独立约束可执行动作。 | 新增状态或调整流转规则时，只需扩展/替换状态策略，减少对 OrderService 主流程的修改。 |
| 工厂模式 | 多类型需求创建校验 | 跑腿、技能、学习、二手需求的创建规则不同，硬编码在 Service 中会破坏开闭原则。 | DemandValidator 统一校验接口；Errand/Skill/Study/SecondhandValidator 独立实现；DemandFactory 根据 category 匹配规则。 | 新增需求板块时新增 Validator 并注册到工厂，DemandService 主逻辑保持稳定。 |
| 观察者模式 | 业务事件解耦通知 | 订单接单、完成、取消后会牵连通知、信用分、需求状态更新，若串行写入服务层会强耦合。 | 业务核心层发布订单事件；通知监听器、信用分监听器分别订阅事件并处理衍生动作。 | 让主交易流程更清晰，也便于异步化、扩展更多事件订阅者。 |
| 组合策略模式 | 智能用户匹配推荐 | 推荐接单用户需要综合位置、技能、信用分等多维因素，单一算法难以覆盖。 | DemandMatcher 定义匹配接口；LocationMatcher、SkillMatcher、CreditScoreMatcher 各自评分；CompositeMatcher 做加权排序。 | 各维度算法可独立替换，组合层统一输出最优候选列表。 |

## 6. Service 业务服务层结构

Service 层是业务逻辑主入口，控制层只负责接收请求和参数校验，跨模块业务通过 Service 接口协作。

| 模块 | Service 类 | 核心职责 |
| --- | --- | --- |
| `auth` | `AuthService` | 用户注册、登录、注销、Token 校验 |
| `auth` | `JwtTokenProvider` | JWT 令牌生成、解析与过期校验 |
| `user` | `UserService` | 个人资料查询、信息修改、公开信息脱敏查询 |
| `user` | `CertificationService` | 实名认证提交、管理员审核、认证状态查询 |
| `user` | `CreditService` | 信用分增减、接单权限校验、信用记录查询 |
| `experiment` | `DemandService` | 需求发布、编辑、取消、分页查询、关键词搜索 |
| `experiment` | `OrderService` | 接单、确认完成、申请取消、定时自动确认 |
| `experiment` | `ReviewService` | 双向评价提交、用户评价列表查询 |
| `experiment` | `ArbitrationService` | 仲裁工单创建、后台处理、待办工单管理 |
| `notification` | `NotificationService` | 消息创建推送、未读统计、单条/全部已读标记 |
| `chat` | `ConversationService` | 会话创建、聊天发送、历史消息查询、会话已读 |
| `recommend` | `RecommendationService` | 需求推荐、接单用户智能匹配 |
| `admin` | `AdminService` | 平台数据看板、用户封禁解封、后台用户列表管理 |

## 7. Controller 接口控制层结构

所有 Controller 统一返回 `ApiResponse<code, message, data>`，鉴权接口统一使用请求头 `Authorization: Bearer <JWT_TOKEN>`。

| Controller | 根路径 | 接口职责 |
| --- | --- | --- |
| `AuthController` | `/api/auth` | 注册、登录、退出登录 |
| `CertificationController` | `/api/certifications` | 提交认证、查询个人认证、管理员审核认证 |
| `UserController` | `/api/users` | 获取个人信息、修改资料、查询他人公开信息、信用记录查询 |
| `DemandController` | `/api/demands` | 发布需求、分页查询需求、需求详情、编辑需求、取消需求 |
| `OrderController` | `/api/orders` | 接单操作、我的订单列表、订单详情、标记完成、确认收货、取消订单 |
| `ReviewController` | `/api/reviews` | 提交双向评价、用户评价列表、订单评价查询 |
| `ArbitrationController` | `/api/arbitrations` | 创建仲裁工单、管理员处理工单、查询待处理工单 |
| `NotificationController` | `/api/notifications` | 通知列表、未读数量、标记已读、一键全部已读 |
| `ConversationController` | `/api/conversations` | 创建私聊会话、会话列表、发送消息、查询历史聊天记录 |
| `AdminController` | `/api/admin` | 平台数据统计看板、用户管理、账号封禁与解封 |
