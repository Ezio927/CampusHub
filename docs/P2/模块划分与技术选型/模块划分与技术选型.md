# 任务 2：模块划分与技术选型（模块化单体架构）

---

## 2.1 模块划分 — 职责边界（基于现有项目结构与已决策）

下面列出本系统每个模块的职责边界，所有模块均在单体工程内实现。

- frontend-ui
  - 职责边界：负责用户界面、路由、页面状态管理与客户端输入校验；与后端通过 REST API 通信，只关心 UI 层展示与交互，不包含任何业务或持久化逻辑。

- web-controller
  - 职责边界：后端 HTTP 接口入口层，负责请求路由、参数校验、鉴权校验（调用 auth）、将请求委派到相应的 Service；只做协议/校验/转换，不直接操作数据库。

- auth
  - 职责边界：负责用户认证与授权（登录、JWT 签发/验证、权限校验）；管理认证相关的安全策略与失效（黑名单等可选）；不负责用户资料管理或业务数据。

- user
  - 职责边界：用户领域业务，负责用户 CRUD、资料维护、用户角色与权限数据的持久化与校验；对外仅暴露 Service 接口，禁止其他模块直接访问其 Repository。

- experiment
  - 职责边界：核心业务域，负责实验/题库的创建、分发、提交与评分流程；负责业务规则、任务分配与结果计算，不负责用户鉴权或通用基础设施。

- persistence
  - 职责边界：统一的数据访问层（Repository/DAO、事务管理），封装与数据库的交互实现；对上层提供标准化的数据访问接口，不包含业务逻辑。

- infra
  - 职责边界：横切基础设施（配置管理、日志、全局异常处理、健康检查、监控接入、公共工具类）；不包含业务逻辑，只提供被其他模块引用的公共能力。

## 2.1 模块划分 — 模块间接口（调用方式、数据格式）

说明：本小节仅定义模块间对外契约（调用方式与数据格式），实现层面遵循“契约先行、Service 为边界”的原则。所有跨模块调用在单体内优先采用方法调用（Java Service 接口）；对外（前端->后端）使用 HTTP REST + JSON，使用统一响应 envelope。

通用约定：
- 认证：HTTP Header 中携带 Authorization: Bearer <JWT>
- Content-Type：application/json
- 时间格式：ISO 8601（例如 2026-05-03T14:30:00Z）
- 分页：标准化为 { page, size, total, items }
- 错误与异常：统一返回 { code, message, data: null, errorId (可选) }

按模块接口示例（简洁准则，仅示例关键接口与 DTO）：

- frontend-ui
  - 调用方式：通过浏览器发起 HTTP REST 请求到 web-controller（或本地 Mock）。
  - 请求示例头：Authorization, Content-Type

- web-controller
  - 对外（前端）：暴露 REST endpoints，负责鉴权与参数校验后调用下游 Service。
  - 示例：POST /api/experiments
    - Request Body (JSON): { "title": "实验A", "description": "...", "ownerId": 123 }
    - Response (统一 envelope): { "code":0, "message":"created", "data": { "id":1001 } }
  - 内部调用：调用 ExperimentService.create(ExperimentCreateDto) 返回 ExperimentDto。

- auth
  - 对外接口：
    - POST /api/auth/login -> Request { username, password } Response { code, data: { token } }
    - POST /api/auth/logout -> Request Header Authorization, Response { code }
  - 内部 Service 接口（Java 样式）：
    - String login(String username, String password)
    - void logout(String token)
    - boolean validate(String token)

- user
  - 对外接口：
    - GET /api/users/{id} -> 返回 UserDto
    - POST /api/users -> Request UserCreateDto
  - DTO 示例：
    - UserDto: { "id":123, "username":"alice", "role":"STUDENT", "createdAt":"2026-05-03T10:00:00Z" }
    - UserCreateDto: { "username":"alice", "password":"***", "role":"STUDENT" }
  - 内部 Service（签名示例）：
    - UserDto getUser(Long id)
    - UserDto createUser(UserCreateDto dto)

- experiment
  - 对外接口（核心）：
    - GET /api/experiments -> 分页返回 { code, data: { items:[ExperimentDto], total } }
    - GET /api/experiments/{id} -> ExperimentDto
    - POST /api/experiments -> ExperimentCreateDto
    - POST /api/experiments/{id}/submissions -> SubmissionCreateDto
  - DTO 示例：
    - ExperimentDto: { "id":1, "title":"实验A", "description":"...", "ownerId":123, "createdAt":"..." }
    - SubmissionCreateDto: { "userId":123, "content":"..." }
    - SubmissionDto: { "id":10, "experimentId":1, "userId":123, "score": 95 }
  - 内部 Service（签名示例）：
    - ExperimentDto createExperiment(ExperimentCreateDto dto)
    - SubmissionDto submit(Long experimentId, SubmissionCreateDto dto)

- persistence
  - 调用方式：不直接对外暴露 REST；由各模块通过 Repository/DAO（Spring Data JPA 接口）访问数据库。
  - 约定：Repository 只由本模块内部的 Service 使用，外部模块通过 Service 接口访问数据。

- infra
  - 对外接口：健康检查 /actuator/health 或 GET /api/health 返回标准化健康信息（同时遵循 envelope）。
  - 提供：全局异常处理、日志采集入口、配置读取接口（仅内部使用）。

接口设计注意事项（工程约束）
- 跨模块必须调用对方 Service 接口，禁止注入/调用 Repository。
- 所有 Controller 方法应添加 OpenAPI 注解以支持契约自动生成。
- 对于可能耗时的操作（文件导出、大量计算），Controller 应返回任务 ID 并通过异步流程或轮询/推送获取结果（避免同步阻塞）。
- 数据敏感性：返回到前端的 DTO 严格过滤敏感字段（如 passwordHash、内部审计字段等）。

## 2.2 技术选型

| 层次 | 已选方案 | 备注 / 实施要点 |
|------|---------|----------------|
| 前端框架 | Vue 3 (Pure JS) + Vite | 已有 `frontend/` 代码基，团队习惯 JS，保证开发速度。Node.js 推荐 18.x LTS。 |
| 后端框架 | Spring Boot 3 + Java 17 | 后端已有启动类，使用 Maven 构建（已有 `pom.xml`）。Spring Boot 生态与教学资源丰富。 |
| 构建工具 | Maven (backend) / npm (frontend) | 后端已有 mvnw；前端使用 package.json。 |
| 数据库（开发） | H2（内存模式） | 便于单元测试与 CI，开发环境使用 Spring profile `dev` 连接 H2。 |
| 数据库（生产） | MySQL 8.x（首选） | ADR 与 Task‑1 建议 MySQL，生产使用 Docker Compose 部署 MySQL，字符集 utf8mb4，设置持久化数据卷。可在未来迁移到 Postgres。 |
| ORM | Spring Data JPA (Hibernate) | 与 Spring Boot 整合，减少样板代码。 |
| 缓存 | Redis（可选） | 用于 JWT 黑名单、热点缓存。通过 Docker Compose 提供可选服务。 |
| 消息队列 | 不引入（初期）/ RabbitMQ 可选 | 若出现异步或高并发场景再引入，避免初期复杂度。 |
| 认证 | JWT + Spring Security | 无状态适合前后端分离。短期 token + 可选 Redis 黑名单策略。 |
| API 文档 | springdoc-openapi (Swagger UI / Knife4j 可选) | 接口先行、代码即文档。生产环境通过配置关闭 UI。 |
| 日志与监控 | Logback 本地 + 可选 ELK/Prometheus | 初期保证日志到文件/控制台；可在 Docker Compose 中加入 Prometheus/Grafana（低优先）。 |
| 容器化/部署 | Docker + Docker Compose | ADR 明确要求 Compose，提供一键本地环境。生产可复用相同镜像与 Compose 文件或扩展到 K8s。 |
| CI/CD | GitHub Actions | 推荐 workflow：编译 → 测试 → 构建镜像（可选）→ 推送制品/通知。 |

实施要点（配置示例与约定）

- 数据库连接
  - dev (H2): spring.profiles.active=dev，spring.datasource.url=jdbc:h2:mem:testdb
  - prod (MySQL): spring.datasource.url=jdbc:mysql://mysql:3306/campushub?characterEncoding=utf8mb4&serverTimezone=UTC
  - 不在仓库提交明文凭证，使用环境变量或 Docker Compose `.env` 注入。

- JWT
  - 密钥通过环境变量注入：JWT_SECRET
  - Token 过期时间按业务设定（例如 1h），必要时提供 refresh token 或短期 token + 黑名单策略。
