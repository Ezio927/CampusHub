# CampusHub Phase 4 交付物 6：AI 代码信任度实验报告

## 1. 实验对象

实验功能点：订单完成后的双向评分与用户平均评分更新。

涉及模块：

- 后端：`demand/service/impl/ReviewServiceImpl.java`
- 后端：`user/entity/User.java`
- 前端：`OrderDetailView.vue`、`MyOrdersView.vue`
- 管理端：`UserManageView.vue`

选择原因：该功能规模适中，但会同时影响订单状态、重复评价、用户评分、额度分奖励和低分仲裁，比较适合观察 AI 代码是否能直接落地。

## 2. Prompt 记录

```text
请为校园互助平台实现订单完成后的双向评分逻辑。
要求：
1. 订单发布者可以评价接单者，接单者可以评价发布者；
2. 每个用户对同一订单只能评价一次；
3. 评分范围为1-5；
4. 只允许订单参与者评价；
5. 用户表保存发布者评分、接单者评分及评分次数；
6. 新评分提交后直接更新平均分；
7. 低分评价触发仲裁，高分评价触发额度分奖励；
8. 给出后端核心代码和必要测试点。
```

## 3. AI 直出结果摘要

AI 给出的初稿可以生成基础 `ReviewService` 逻辑，包含评分范围检查、订单参与者判断、保存评价记录和更新用户平均分。前端也给出了一个简单的星级评分表单。

未直接采用完整代码，只保留了部分结构思路，原因是 AI 初稿与项目已有分层和业务规则存在偏差。

## 4. 人工检查发现的问题

| 问题 | 影响 | 人工处理 |
| --- | --- | --- |
| 只维护一个 `ratingAvg`，没有区分“作为发布者收到的评分”和“作为接单者收到的评分” | 悬浮栏和个人主页无法区分身份评分 | 拆成 `publisherRating/publisherRatingCount` 与 `acceptorRating/acceptorRatingCount` |
| 重复评价判断不完整，只按订单和被评价人判断 | 可能误拦截另一方评价，或漏掉同一评价人重复提交 | 改为 `orderId + reviewerId` 唯一判断 |
| 没有事务边界 | 保存评价成功但用户平均分更新失败时会产生不一致 | 在提交评价服务上增加事务 |
| 低分/高分副作用处理过于简单 | 不能接入已有仲裁和额度分体系 | 低分调用仲裁服务，高分调用额度分奖励服务 |

## 5. 修复前后对比

| 指标 | AI 直出 | 人工审查修复后 |
| --- | --- | --- |
| 编译是否通过 | 基本通过，但需适配现有 Repository/DTO 命名 | 通过 |
| 功能是否可运行 | 可提交简单评分 | 可完成双向评分、重复评价限制、平均分更新 |
| 实验用例通过情况 | 5/8 | 8/8 |
| 主要问题 | 身份评分混淆、重复判断不严、缺事务、副作用遗漏 | 已修复 |

实验用例共 8 个：发布者评价接单者、接单者评价发布者、重复评价、非参与者评价、非法评分、未完成订单评价、低分仲裁、高分额度分奖励。

## 6. 最终验证

本地最终验证时间：2026-06-07。

| 验证项 | 结果 |
| --- | --- |
| 后端 `.\mvnw.cmd test` | 128 tests, 0 failures, 0 errors |
| 前端 `npm run build` | 构建成功，有 1 条动态导入分包警告，不影响运行 |

结论：AI 适合生成评分流程的骨架，但涉及“身份语义”和“跨模块副作用”的部分必须人工审查。
