## 1. 修复概览

本阶段的 Bug 主要集中在两类问题：一类是功能合并后带来的构建错误和页面冲突，另一类是联调过程中暴露出来的业务规则漏洞，比如封禁用户还能走到发单流程、单人可以通过脚本刷大量订单、聊天图片格式判断不稳定等。

整体修复思路不是“哪里报错补哪里”，而是尽量把规则放回后端兜底：前端负责提示和交互，后端负责权限、频率、封禁、隐私脱敏等硬约束。这样演示时更稳，也不会因为绕过前端就破坏业务逻辑。

## 2. Bug 修复明细

### Bug-01：合并后 ProfileView 模板解析失败

**问题现象：**  
合并通知分支后，前端出现构建错误，个人中心页面 `ProfileView` 无法正常解析，页面无法稳定打开。

**根因分析：**  
通知功能分支和 `dev` 分支都改动了个人中心相关页面，合并时出现了模板片段重复、标签闭合不完整、变量引用不一致等问题。这个问题不是单个语法点造成的，而是合并冲突处理后残留了多个小错误。

**修复方案：**  
先用 `dev` 的干净版本作为基准重写 `ProfileView`，再把通知入口、个人资料展示等新增内容逐步补回去。同时修复合并冲突引入的 4 个前端构建错误。

**验证结果：**  
前端重新构建通过，个人中心页面可正常进入，个人资料、通知入口和菜单跳转没有再出现白屏。

**关联记录：** `1f794e6 fix: 用 dev 干净版本重写 ProfileView 修复模板解析错误`；`3495b4a fix: 修复合并冲突导致的4个前端构建错误`。

### Bug-02：系统通知功能合并后链路不稳定

**问题现象：**  
系统通知功能单独开发时可用，但合并到 `dev` 后，与原有用户页面、导航和订单流程存在冲突。部分通知入口不显示，部分通知状态更新不稳定。

**根因分析：**  
通知模块涉及前端页面、后端接口、订单事件触发和用户消息读取状态，跨模块点比较多。分支合并时如果只保留一侧代码，很容易丢掉另一侧已有功能。

**修复方案：**  
处理 `feat/system-notification` 与 `dev` 的冲突，保留双方新增功能：系统通知列表、管理员通知、未读状态、与订单/仲裁相关的通知入口。前端导航也同步补上通知入口。

**验证结果：**  
系统通知页面可以正常访问，通知列表能够展示，已读/未读状态能够更新。订单和管理员相关通知在联调中可以正常触发。

**关联记录：** `3215418 feat: 实现系统通知完整功能`；`c4ef416 fix: 解决 notification 合并 dev 的冲突，保留双方新增功能`。

### Bug-03：封禁用户发单时提示“未实名认证”

**问题现象：**  
联调时发现，账号被封禁后再发布订单，页面提示的是“未实名认证”，而不是“账号已被封禁”。这个提示会误导用户，也不利于管理员解释处理结果。

**根因分析：**  
后端校验顺序不合理：接口先判断实名认证状态，再判断封禁状态。对于被封禁用户，如果同时存在认证状态异常或状态字段未同步，就会优先返回“未实名认证”。

**修复方案：**  
调整发布订单、接单等关键接口的权限判断顺序：先检查账号是否被封禁，再检查实名认证、信用分等其他条件。同时补充封禁申诉入口，避免用户只看到错误提示但没有后续处理路径。

**验证结果：**  
封禁用户再次发单时会被明确拦截，提示与封禁状态一致；正常用户仍按实名认证和信用分规则继续校验。

**关联记录：** `0538a9d feat: 新增封禁申诉 信用分申诉 订单纠纷申诉 评价申诉功能`；聊天记录中“在封禁下发订单会提示未实名认证”。

### Bug-04：单人可通过脚本连续发布大量订单

**问题现象：**  
联调时发现，如果用自动化脚本连续调用发单接口，单个用户可以在短时间内发布几百个订单，导致需求列表被刷屏，其他人的订单被淹没。

**根因分析：**  
原来的限制主要依赖前端交互，没有在后端建立“频率限制”。只要绕过页面直接请求接口，就能连续发布订单、发送私信或提交举报。

**修复方案：**  
在后端增加操作频率限制，覆盖发单、私信、举报、接单、仲裁申请等高风险入口。限制规则按用户维度记录，超过阈值后直接拒绝请求，避免恶意脚本影响平台正常使用。

**验证结果：**  
脚本连续请求时会被限流，正常手动操作不受影响。该修复也降低了私信刷屏和举报刷屏的风险。

**关联记录：** `b211461 feat(backend): 为发单私信举报接单仲裁增加操作频率限制`；聊天记录中“设置单人每日订单上限”。

### Bug-05：私信图片上传格式判断异常

**问题现象：**  
私信中发送图片时出现问题。页面提示“图片格式仅支持 png、jpg、gif、webp”，但实际选择 JPG 图片时仍可能弹出格式错误。

**根因分析：**  
前端图片校验逻辑不够统一：有的地方按文件后缀判断，有的地方按 MIME 类型判断；同时没有统一处理 `.jpg` / `.jpeg`、大小写后缀等情况。聊天图片和其他图片上传入口的规则也没有完全对齐。

**修复方案：**  
统一图片格式校验规则：允许 `png / jpg / jpeg / gif / webp`，后缀统一转小写后再判断；错误提示也统一为同一套文案。对于不符合格式的文件，前端直接拦截，避免继续请求后端。

**验证结果：**  
PNG、JPG/JPEG、GIF、WEBP 图片均可正常进入发送流程；非图片文件会被拦截并给出明确提示。

### Bug-06：用户公开接口存在未登录访问和信息暴露风险

**问题现象：**  
联调中发现部分用户信息接口可以在未登录状态下访问，且返回字段偏多。对于校园互助平台来说，手机号、邮箱、真实姓名等信息不能随意暴露。

**根因分析：**  
用户公开信息接口没有严格区分“本人信息”和“他人公开信息”。接口层鉴权与 DTO 脱敏没有完全落实，导致前端虽然不展示敏感字段，但后端响应中仍可能带出多余信息。

**修复方案：**  
限制用户公开接口的未登录访问；对他人信息只返回头像、昵称、信用分、公开评价等必要字段。手机号、邮箱、学号等敏感字段进行脱敏或不返回。

**验证结果：**  
未登录访问受限；登录后查看他人资料只展示部分公开信息；发布订单或接单后的必要联系信息也按业务场景控制可见范围。

**关联记录：** `4caf418 fix(backend): 限制用户公开接口未登录访问并脱敏返回字段`。

### Bug-07：黑名单功能没有完全接入业务入口

**问题现象：**  
黑名单功能完成后，部分页面可以添加或查看黑名单，但在私信、接单等业务入口处没有完全生效，容易出现“拉黑了但还能互动”的情况。

**根因分析：**  
黑名单最初偏向页面功能，业务校验没有同步接入所有交互入口。只在展示层限制是不够的，用户仍可能通过接口直接发起互动。

**修复方案：**  
补充黑名单管理逻辑，并在私信、查看对方部分信息、订单互动等关键入口增加后端校验。前端同步给出更清楚的提示，避免用户误以为操作失败是系统错误。

**验证结果：**  
黑名单关系建立后，被拉黑用户无法继续通过对应入口发起互动；解除黑名单后功能恢复。

**关联记录：** `140dcff fix: 增加了黑名单功能`。

### Bug-08：缺少申诉入口，用户被处罚后处理链路不完整

**问题现象：**  
封禁、扣信用分、订单纠纷、评价争议这些处理都能发生，但用户侧原本缺少统一申诉入口。被处罚用户只能线下找管理员，系统内没有闭环。

**根因分析：**  
原设计更关注管理员“处理问题”，但对用户“申诉和解释”的流程考虑不足。这样会导致后台操作有结果，但用户侧缺少可追踪记录。

**修复方案：**  
新增封禁申诉、信用分申诉、订单纠纷申诉、评价申诉功能；登录页底部补充管理员联系邮箱，作为系统内申诉不可用时的兜底渠道。

**验证结果：**  
用户可以从相关入口提交申诉，管理员可以看到申诉记录并处理。即使账号受限，也能通过页面提示或邮箱找到处理方式。

**关联记录：** `0538a9d feat: 新增了封禁申诉 信用分申诉 订单纠纷申诉 评价申诉功能`；`d69fc54 feat: 登录页底部添加管理员联系邮箱，便于线下申诉`。

### Bug-09：启动脚本和后端编译错误影响联调效率

**问题现象：**  
多次切换分支和重启项目后，`8080`、`5173` 端口容易被旧进程占用；同时合并后出现过后端编译错误，影响大家本地联调。

**根因分析：**  
开发阶段频繁启动前后端，旧进程未释放会造成端口冲突。合并多个功能分支后，后端依赖、接口签名或实体字段也可能出现不一致。

**修复方案：**  
优化启动脚本，在启动开发环境前自动释放常用端口；修复后端编译错误，保证 `dev` 分支可以作为稳定联调基准。

**验证结果：**  
本地启动流程更稳定，减少了“不是业务 Bug、但卡住所有人”的环境问题。后续联调主要集中在业务逻辑本身。

**关联记录：** `847c87c fix(scripts): 启动开发脚本前自动释放 8080 与 5173 端口`；`628aab7 fix: 修改了启动脚本和后端编译错误`。

### Bug-10：菜单栏和导航状态不统一

**问题现象：**  
前端页面改为横向导航后，菜单项命名不统一，部分页面选中状态不明显，用户不知道自己当前在哪个模块。

**根因分析：**  
旧版 SideBar 和新版横向导航的样式、命名规则同时存在，造成体验不一致。部分路由没有配置 active 状态，点击后没有明显高亮。

**修复方案：**  
统一菜单格式，删除废弃 SideBar；导航项统一为四字风格；给顶部导航栏补充 `active-class` 高亮。顺手清理了非必要 emoji，保持页面风格一致。

**验证结果：**  
页面导航更清楚，演示时能快速切换用户中心、订单、通知、申诉等模块，不再出现明显的菜单混乱。

**关联记录：** `535f765 refactor: 统一菜单格式，删除废弃 SideBar，导航项全部改为四字`；`1417e62 fix: 顶部导航栏选中状态添加 active-class 高亮显示`；`fc17e1a refactor: 清除所有页面 emoji，仅保留 ChatView 表情选择器`。
