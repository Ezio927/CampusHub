# CampusHub Phase 4 交付物 1：Sprint 合并任务看板

---

## 1. 任务一目标

本交付物用于将 Phase 4 的 P0、P1 与可选 P2 功能合并为一个可执行 Sprint 看板，明确每项任务的优先级、模块、拆解内容、估计工时、负责人、当前状态与完成标准。

任务拆解遵循以下原则：

1. **P0 必须完成**：用户管理、需求发布、订单管理是最小可演示闭环。
2. **P1 基本完成**：评价与信用体系、消息通知至少完成核心链路。
3. **P2 可选降级**：智能匹配、管理后台只作为轻量扩展，不影响 P0/P1 稳定性。
4. **单项任务 2-4 小时内可完成**：避免任务过大导致无法跟踪。
5. **测试与联调单独排期**：单元测试、集成测试、前后端联调不挤占功能开发时间。

## 3. AI 辅助 Sprint 规划记录

### 3.1 输入给 AI 的 Prompt

```text
请根据 CampusHub 校园互助平台 Phase 4 编码开发要求，以及以下优先级列表，帮我们拆分 Sprint 任务：
P0 用户管理：注册、登录、个人资料管理；
P0 需求发布：发布需求、需求列表、需求详情；
P0 订单管理：接单、状态流转、订单历史；
P1 评价与信用体系：双向评分、信用分计算；
P1 消息通知：通知触发、消息模板、通知记录；
P2 扩展功能：智能匹配、管理后台等；
测试保障：单元测试、集成测试、联调验证。
要求每个任务 2-4 小时，包含优先级、模块、任务、估计工时、负责人、完成标准和风险。
```

### 3.2 AI 原始输出摘要（存在瑕疵）

| AI 原始建议 | 主要问题 |
| --- | --- |
| 将“需求发布、需求列表、需求详情”合并为 8 小时大任务 | 超出 2-4 小时粒度，难以跟踪进度 |
| 将“智能匹配 + 管理后台”列为必须完成 | 与 P2 可选性质不一致，可能挤压 P0/P1 时间 |
| 未单独安排重复接单、越权访问、未登录访问等异常流程测试 | 仍偏向 happy path，测试覆盖不足 |
| 订单状态流转建议直接在 Controller 中判断状态 | 不符合 P3 详细设计中的 Service 编排与状态策略思路 |
| 消息通知只写“发送通知”，没有区分触发时机、模板、记录查询 | 任务边界不清，验收困难 |

### 3.3 人工审查与修正结论

团队对 AI 初稿做了以下修正：

1. 将所有超过 4 小时的任务拆成更小的开发项。
2. 将 P2 明确降级为“有时间再做的轻量版”，不阻塞 P0/P1。
3. 对订单管理补充并发接单冲突、状态不可逆、订单历史记录等验收点。
4. 对测试任务单独排期，覆盖 1 个完整正常流程和至少 2 个异常流程。
5. 保持架构约束：Controller 只做请求入口，核心业务通过 Service 完成，不跨模块直接调用 Repository。

## 4. 最终 Sprint 合并任务看板

> 成员 A：后端用户/认证；成员 B：后端需求/订单；成员 C：前端页面/交互；成员 D：测试集成/通知。

| 编号 | 优先级 | 模块 | 任务拆解 | 估计工时 | 负责人 | 状态 | 完成标准 |

| T1 | P0 | 用户管理 | 注册、登录、JWT 鉴权接口实现 | 3h | 成员 A | 待开发 | 注册成功后生成用户；登录返回令牌；未登录接口返回统一错误码 |
| T2 | P0 | 用户管理 | 当前用户信息查询与个人资料修改 | 2h | 成员 A + 成员 C | 待开发 | 当前用户信息接口可查询；资料可修改；手机号/邮箱按规则脱敏展示 |
| T3 | P0 | 需求发布 | 发布需求接口与板块校验 | 3h | 成员 B | 待开发 | 四类需求均可发布；必填字段和板块特有规则生效 |
| T4 | P0 | 需求发布 | 需求列表、筛选与详情页联调 | 3h | 成员 B + 成员 C | 待开发 | 前端可查看需求列表、按状态/分类筛选、进入详情页 |

## 6. 风险识别与降级策略

| 风险编号 | 风险描述 | 影响范围 | 应对策略 |
| --- | --- | --- | --- |
| R1 | 订单状态流转逻辑复杂，容易出现状态越权或重复操作 | P0 订单管理 | 按状态策略思路集中在 Service 层校验；为重复接单和取消后操作补测试 |
| R2 | 前后端字段名不一致，导致联调失败 | P0/P1 全流程 | 以 API 文档为准；联调前先用 Postman/Swagger 验证返回字段 |
| R3 | 评价与信用体系可能引发连锁更新，出现事务边界不清 | P1 评价与信用 | 先实现同步 Service 编排；信用记录必须写入流水，便于回溯 |
| R4 | 消息通知容易重复触发或漏触发 | P1 消息通知 | 明确触发事件：接单、完成、取消、评价；先做站内通知，不做实时推送 |
| R5 | P2 功能消耗时间，影响核心功能稳定性 | P2 扩展功能 | P2 只做轻量版；若 P0/P1 未全部通过测试，直接延期 |
| R6 | AI 生成测试可能只覆盖正常路径 | 测试保障 | 人工补充未登录、重复接单、越权操作等异常用例 |

## 7. 功能范围确认

### 7.1 必须交付范围

- 用户注册、登录、JWT 鉴权。
- 当前用户资料查询和修改。
- 需求发布、列表、筛选、详情查看。
- 接单、订单状态流转、订单历史。
- 统一响应格式与全局异常处理。
- 核心单元测试与集成测试。

### 7.2 基本交付范围

- 双向评价。
- 信用分计算与信用记录。
- 站内通知记录和已读状态。

### 7.3 可降级或延期范围

- 智能匹配的复杂排序算法。
- 完整管理后台。
- 实时 WebSocket 通知。
- 高级数据统计看板。
